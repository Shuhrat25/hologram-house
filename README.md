# Голограммная витрина 3D-моделей

[Открыть демо](https://hologram-house.vercel.app/)

Просмотрщик 3D-объектов на **React + Three.js (react-three-fiber)** с двумя режимами:

- **Реальный вид** — исходные PBR-материалы модели с трёхточечным светом и тенями.
  Открывается первым;
- **Голограмма** — кастомные GLSL-шейдеры в духе `studio.tripo3d.ai`. Пользователь
  включает её сам, и каждое включение заново проигрывает материализацию.

Переключение — кнопками на панели или клавишами **H** / **Пробел**.

## Запуск

```bash
npm install
npm run dev
```

Прод-сборка: `npm run build`, предпросмотр — `npm run preview`.

> При правке шейдеров делайте полную перезагрузку страницы: HMR подменяет модуль
> материала, но оставляет старые юниформы, и картинка «залипает».

## Объекты

Переключатель — карточки с превью у левого края кадра (на узком экране уезжают под шапку).
Смена объекта полностью перезапускает сцену и сборку.

|---|---|---|---|---|

| Horned Titan | 329 746 | 2.9 МБ | iRahulRajput | CC BY 4.0 |
| Da Vinci Sword | 35 769 | 2.5 МБ | nodgerty | CC BY 4.0 |
| 343 Guilty Spark | 120 801 | 1.9 МБ | jameslucino117 | CC BY 4.0 |

### Как готовить новую модель

Исходники были непригодны для веба: Титан весил **50.7 МБ**, а Guilty Spark и вовсе
не загрузился бы — он требовал `KHR_materials_pbrSpecularGlossiness`, поддержку которого
three.js выкинул. Оба прогнаны через glTF-Transform:

```bash
npx @gltf-transform/cli metalrough in.glb tmp.glb
```

```bash
npx @gltf-transform/cli optimize tmp.glb public/models/out.glb --compress meshopt --texture-compress webp --texture-size 1024 --simplify-ratio 0.35 --simplify-error 0.0002
```

Первая команда переводит спекуляр-глянец в металл-шероховатость: без неё `GLTFLoader`
падает на required-расширении. Вторая жмёт геометрию и текстуры.

Результат: 50.7 МБ → 2.5 МБ и 13.6 МБ → 1.9 МБ. `--simplify-ratio` подбирается на глаз:
на агрессивном `--simplify-error 0.001` от Титана осталось 42k треугольников вместо 942k,
детализация рассыпалась. Ratio 0.35 даёт 330k и выглядит целым.

У модели должны остаться атрибуты `POSITION`, `NORMAL` и индексы — `mergeGeometry.ts`
сливает всё в один буфер именно по ним. Новый объект добавляется строкой в `MODELS`
(`src/settings.ts`).

### KTX2 / Basis

Обычные PNG, JPEG и WebP в видеопамяти разворачиваются в сырой RGBA. У меча исходно
четыре текстуры 4096×4096 — это **340 МБ видеопамяти**. KTX2 (расширение glTF
`KHR_texture_basisu`) держит текстуру сжатой прямо в видеопамяти: транскодируется
в BC7 на десктопе, в ASTC/ETC на мобильных.

Подключено: транскодер лежит в `public/basis/` (без CDN), `KTX2Loader` цепляется
к `useGLTF` через `extendLoader` в `ModelStage.tsx`. Загрузчик берётся из
`three-stdlib`, а не из `three/examples` — drei собирает `GLTFLoader` оттуда же,
иначе `setKTX2Loader` не сходится по типам.

Для кодирования нужен **KTX-Software 4.4+**: gltf-transform не кодирует сам, он
вызывает нативный бинарник `ktx`
([релизы](https://github.com/KhronosGroup/KTX-Software/releases)). Пятая версия
не годится — там убраны legacy-инструменты и меняется API.

```bash
gltf-transform optimize in.glb t1.glb --compress meshopt --texture-compress auto --texture-size 2048 --simplify false
gltf-transform etc1s t1.glb t2.glb --quality 240 --mipmaps true
gltf-transform meshopt t2.glb out.glb --level high
```

Третий шаг обязателен: `etc1s` распаковывает `EXT_meshopt_compression`, и геометрию
нужно сжать заново.

| Модель | WebP | KTX2 | Видеопамять |
|---|---|---|---|
| Da Vinci Sword | 1.6 МБ | 2.5 МБ | 89 МБ → ~22 МБ |
| Horned Titan | 2.6 МБ | 2.9 МБ | 17 МБ → ~4 МБ |

Файл растёт примерно на 10–50%, видеопамять падает вчетверо.

**UASTC не используем.** Попытка отдать ему нормал-карты и ORM раздула меч до 8.9 МБ
при той же экономии видеопамяти — в BC7 транскодируются оба режима одинаково,
разница только в качестве и весе файла.

**Дом и Guilty Spark остались на WebP.** KTX-энкодер принимает только PNG и JPEG,
а их текстуры авторы отдали уже в WebP: `optimize --texture-compress ktx2` честно
пишет `Skipping, unsupported texture type "image/webp"`. Потери невелики — у обоих
текстуры мелкие (у дома 73 штуки по 256²). Если понадобится, путь такой: декодировать
WebP в PNG сторонним инструментом, затем обычная цепочка.

### Превью для карточек

Превью — настоящие кадры из приложения, лежат в `public/thumbs/<id>.png`.
Снимаются dev-эндпоинтом из `vite.config.ts`: страница берёт кадр канваса и POST-ит
data-URL на `/__thumb/<id>`, плагин пишет файл. В прод-сборку эндпоинт не попадает,
а `preserveDrawingBuffer`, нужный для съёмки, включён только в dev.

Пересъёмка — из консоли браузера на запущенном dev-сервере: для каждой карточки
кликнуть по ней, включить режим голограммы, дождаться сборки, вырезать из канваса
квадрат 96×96 и отправить его POST-ом на `/__thumb/<id>`.

## Из чего сложен эффект голограммы

### Три прохода по одной геометрии

Требование — **спереди поверхность гладкая, но сквозь неё читается начинка**.
Обычная полупрозрачность так не умеет: она складывает все слои подряд и даёт кашу.
Поэтому одна и та же геометрия рисуется тремя проходами с общим набором юниформ
(`src/three/hologramMaterial.ts`):

| Проход | `depthFunc` | Что делает |
|---|---|---|
| `depth` | `LessEqual`, пишет глубину, `colorWrite: false` | прибивает ближайшую поверхность и даёт early-Z остальным |
| `ghost` | `Greater`, аддитивно | всё, что **за** первым слоем — контуры и рёбра начинки |
| `front` | `LessEqual`, alpha-over | сам голограммный слой, ровно один, без наложений |

Обе прозрачности задаются в процентах: **Оболочка** (75%) и **Начинка** (45%).
У начинки процент намеренно ниже — тонкая внешняя поверхность и плотная внутренняя
дают тот самый «рентген». Начинка не умножается на прозрачность оболочки: иначе
тонкая оболочка гасила бы заодно и то, ради чего она тонкая.

В `ghost` и контуры, и рёбра гасятся к нормали — иначе плоские полы внутри дома
засвечивают кадр целиком.

### Сетка только на скользящих углах

`grid *= smoothstep(0.04, 0.46, fres)` — там, где поверхность смотрит на камеру,
сетка гаснет полностью и остаётся чистое стекло; проявляется она к силуэту.
Сама сетка — триплан по мировым координатам с `fwidth`, поэтому линии имеют
постоянную толщину на экране и не зависят от UV-развёртки модели.

### Появление: лучи сверху → сборка снизу вверх

1. `MatrixRain.tsx` — полноэкранный квад (позиция пишется прямо в NDC, камера на
   него не влияет) с падающими колонками псевдосимволов по бокам кадра;
2. `IntroRays.tsx` — 180 аддитивных лучей, бьющих из дронов вниз: луч ТЯНЕТСЯ
   от дрона к цели сплошной линией, разгораясь к точке касания, и гаснет,
   когда его участок собран;
3. модель проявляется в вершинном шейдере **снизу вверх**: задержка куска задаётся
   его высотой (`delay = h * 0.68`), и пока кусок не проявился, он светится тем
   сильнее, чем меньше собран. Куски возникают на своих местах, без разлёта — за
   него отвечает `uSpread`, по умолчанию 0.

Луч и его участок модели используют одну и ту же кривую, поэтому голова луча
приходит ровно в тот момент, когда этот участок материализуется.

Объект собирается с пустого места: `depth`-проход делает `discard` там, где ещё
ничего не проявилось (иначе невидимая геометрия прибивает глубину и прячет уже
собранное), а текстурированная модель при переходе гаснет быстрее, чем идёт сборка.

Прогресс сборки считается по **настенным часам**, а не по накопленным кадрам —
иначе при просадке fps появление растягивалось бы на десятки секунд.

### Дроны-строители

Лучи бьют не из пустоты: их источник — три Guilty Spark, которые влетают, зависают
над объектом, строят его и улетают. Весь таймлайн собран в `three/introTimeline.ts`,
чтобы дроны, лучи, дождь и сборка читали одни и те же границы.

| Фаза | Доля таймлайна |
|---|---|
| влёт дронов | 0 → 0.17 |
| сборка объекта и лучи | 0.15 → 0.82 |
| пауза «скан завершён» | 0.82 → 0.9 |
| отлёт | 0.9 → 1 |

Высота дронов идёт **над фронтом сборки** (`height * (0.95 + build * 0.85)`): они
поднимаются вместе с тем, что строят, и свет всегда падает сверху вниз. Начало луча
берётся из позиции дрона через юниформ `uEmitters`, а конец запечён в геометрию —
поэтому вершинный буфер не перестраивается ни разу за кадр.

Любое касание камеры взводит `skipRef` и досматривает интро мгновенно.

**Про полигоны.** Полная модель Spark — 121k треугольников, три штуки в нашей
трёхпроходной схеме дали бы больше миллиона. Поэтому у дронов отдельный упрощённый
файл `spark_drone.glb` (74k) и **один** проход простым материалом: в кадре они мелкие,
и «рентген» на них всё равно не читается. Итог — 225k треугольников за три вызова
отрисовки, интро идёт в 60+ fps.

### Глитч вспышками

Глитч не двигает вершины: поверхность разбита на ячейки, каждая с дискретным шагом
времени вспыхивает или гаснет, плюс изредка пробегает яркая строка-разряд. Геометрия
остаётся неподвижной — иначе depth-prepass разошёлся бы с основным проходом.

Помехи приходят **короткой вспышкой раз в несколько секунд**, а не идут постоянно:
базовый период 3.6 с со случайным разбросом, чтобы не было метронома, длительность
вспышки около 0.3 с. Между вспышками картинка чистая.

### Свечение вокруг объекта

Это ни `box-shadow`, ни виньетка: первый живёт в CSS и про силуэт внутри канваса
ничего не знает, вторая затемняет края кадра, а не подсвечивает объект. Работают две
вещи: **Bloom** даёт ореол вокруг ярких пикселей самой модели, а `Backdrop.tsx` рисует
радиальную подложку, слегка подкрашенную цветом проекции. Виньетка поверх остаётся —
она лишь дожимает углы.

### Сцена

Вокруг модели ничего нет: ни пола-сетки, ни площадки, ни отражения — только
объект в пустоте. Поверх — Bloom, хроматическая аберрация, шум и виньетка.

## Производительность

Четыре вещи, без которых сцена ощутимо подтормаживала:

**Обычным материалам не включаем прозрачность.** Сначала кроссфейд между режимами был
сделан анимацией `opacity`, для чего всем материалам ставился `transparent = true`.
Это отправляет каждый меш в прозрачную очередь: пересортировка по глубине каждый кадр,
отключённый early-Z, блендинг на всём. На доме из 75 мешей с мебелью за стенами это
било по кадру сильнее всего. Теперь обычная модель переключается мгновенно, а
растворяется поверх неё голограмма — прозрачными остаются только те 18 материалов,
которым это нужно по смыслу (листва, стёкла, вода).

**Карта теней статична.** Свет и модель не двигаются, так что пересчитывать
2048×2048 по 466k треугольников каждый кадр незачем: `shadow.autoUpdate = false`,
а `needsUpdate` взводится при смене режима или объекта. Это снимает с кадра целый
проход по всей геометрии.

**Разрешение падает на время вращения** — `AdaptiveDpr` плюс `performance.regress()`.
Порог `performance.min` = 0.85: просадка почти не видна глазом. Ниже картинка
начинает мылить на каждое касание, и это раздражает сильнее, чем помогает —
0.6 и 0.35 пробовали, оба заметны.
Важная тонкость: встроенный проп `regress` у `OrbitControls` использовать нельзя,
если включено автовращение — контролы шлют `change` каждый кадр, и качество просядет
навсегда. Поэтому `regress()` вызывается вручную и только между `onStart` и `onEnd`,
то есть пока пользователь реально тянет мышью.

**Проход начинки отключается во время вращения.** Из трёх проходов `ghost` самый
дорогой: он рисует всё, что за первым слоем, и early-Z ему ничем не помогает.
Пока камеру крутят, его видимость снимается, а как только отпустили — возвращается.

## Камера

По умолчанию — `OrbitControls` на **полной сфере**: 360° по горизонтали и по
вертикали, включая вид снизу (полярный угол не ограничен).

**Демпфирование выключено** (`enableDamping={false}`, у `TrackballControls` —
`staticMoving`). С инерцией камера догоняет курсор с задержкой: при резкой смене
направления объект ещё доворачивает влево, когда мышь уже ушла вправо, и это
читается как лаг, а не как плавность. Без неё поворот идёт ровно за курсором
и встаёт в момент отпускания. Галочка
**«Свободное вращение X / Y / Z»** переключает на `TrackballControls` —
свободное вращение по всем трём осям, включая крен.

Дистанция считается по габаритной сфере модели и **узкой из двух сторон экрана**,
иначе на вытянутом окне объект вылезает за края.

## Стек

| Пакет | Роль |
|---|---|
| `three` | рендер |
| `@react-three/fiber` | React-обвязка Three.js |
| `@react-three/drei` | `useGLTF`, `OrbitControls`, `TrackballControls`, `useProgress` |
| `@react-three/postprocessing` | Bloom, хроматическая аберрация, шум, виньетка |

> React зафиксирован на `19.2.8`: `@react-three/fiber@9.7` пока требует `react >=19 <19.3`.

Все модели используют `EXT_meshopt_compression`, `KHR_mesh_quantization` и
`EXT_texture_webp`. Декодер meshopt подключает `useGLTF` из drei (включён по умолчанию),
WebP распаковывается браузером нативно.

## Структура

```
src/
  settings.ts                  Settings, палитры, реестр MODELS
  components/
    Scene.tsx                  Canvas, свет, камеры, постобработка
    ModelStage.tsx             загрузка GLB, нормализация, три прохода, кроссфейд
    MatrixRain.tsx             матричный дождь на фоне во время появления
    IntroDrones.tsx            три Guilty Spark: влёт, работа, отлёт
    IntroRays.tsx              лучи, бьющие из дронов
    Backdrop.tsx               радиальная подложка: свечение вокруг объекта
  three/
    hologramMaterial.ts        шейдеры голограммы и фабрика трёх проходов
    introTimeline.ts           границы фаз появления, общие для всех участников
    mergeGeometry.ts           сборка мешей в один буфер
  ui/
    ControlPanel.tsx           панель управления
    ModelSwitcher.tsx          карточки объектов с превью
    Loader.tsx                 экран загрузки
```

Два решения, важных для тяжёлых моделей:

- **Геометрия сливается в один буфер.** Меши делят одни материалы, так что каждый
  проход — это один вызов отрисовки. Сборка идёт за **один** проход в заранее
  выделенные массивы: наивный путь (временная `BufferGeometry` на каждый меш,
  затем `applyMatrix4`, затем `mergeGeometries`) — это три полных прохода по
  вершинам и десятки объектов на выброс, и на 512k вершин он подвешивал кадр
  при смене объекта. Матрица применяется вручную ещё и потому, что
  `applyMatrix4` по нормализованным `Int16`-позициям (`KHR_mesh_quantization`)
  писал бы дробные значения в целочисленный массив и рвал модель.
  Результат кешируется по объекту, так что возврат к уже виденному — мгновенный.
- **Тонемап `NeutralToneMapping`** — ACES уводил насыщенный циан в оранжевый на пересветах.

| Действие | Как |

| Поворот 360° / зум / сдвиг | ЛКМ · колесо · ПКМ |
